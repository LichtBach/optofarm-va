## 1. Provider names and branch addresses now arrive corrected

Evolvo stores every one of its 16 provider names, and all 8 branch addresses, with the diacritics
stripped. Four new nodes (`CA / BOOK / FIND / MAN Display Names`) rewrite them on the way out — in
both success *and* error responses. Evolvo itself is never written to.

**Five provider names changed:**

| evolvo stores | you now receive |
|---|---|
| `Dr. Ilovan Anca` | `Dr. Ilovan Anica` |
| `Dr. Prof. Szekely Attila  - Consiliere / Terapie psiho-ortoptica` | `Dr. Prof. Székely Attila - Consiliere / Terapie psiho-ortoptica` |
| `Optometrist Bodi Ildiko` | `Optometrist Bódi Ildikó` |
| `Optometrist Ifj Jeremias Laszlo` | `Optometrist Ifj. Jeremiás László` |
| `Optometrist Jeremias Zoltan` | `Optometrist Jeremiás Zoltán` |

The other eleven are unchanged. **`Anca` → `Anica` is not a diacritic** — it was the wrong given
name, confirmed by the clinic. `Ifj` also regained its period.

Romanian provider names (`Ormenisan`, `Zait`) deliberately keep their stripped spellings — the
clinic's decision. The Romanian *voice* handles that in the dictionary instead.

**All 8 branch addresses gained their Romanian diacritics:** `Tg. Mureș, Str. Poștei Nr. 3`,
`Tg. Mureș, Piața Trandafirilor 53`, `Reghin, Str. Școlii 11`, `Sovata, Str Principală 196`, and so
on. Abbreviations are deliberately **not** expanded — `Tg.` stays `Tg.`. See §3 for why.

### You do not need to do anything with these

Send a corrected name or address straight back into a tool and it still matches. Verified live,
including `"Bódi Ildikó doktornőhöz"` with the Hungarian case ending and
`{"doctor": "Dr. Ilovan Anica", "location": "Tg. Mureș, Str. Poștei Nr. 3"}` echoed verbatim.

**Do not translate a corrected name back to the old spelling before sending it.** The matcher strips
diacritics on both sides, and `Anca`/`Anica` is one edit inside its tolerance. The fuzzy logic that
recovered `Kilován` → `Dr. Ilovan Anca` on the 2026-09-16 call is untouched and still passes.

The `Ifj.` rule is unchanged: **say it, don't send it.** It is what distinguishes father from son.

## 3. The rule that constrains both halves

**Diacritics are fixed in n8n. Abbreviation expansion belongs in the pronunciation dictionary.**

This is not stylistic. Restoring a diacritic is free, because the matcher strips diacritics on both
sides before comparing. Expanding `Tg.` → `Târgu` is three edits against a Levenshtein budget of two:
measured against the live matcher, pushing it through n8n sent **all six Târgu branches to NO MATCH**
when a corrected address was echoed back into a tool. A dictionary alias never reaches a matcher, so
expansion is safe there and nowhere else.

If you ever want a spoken form that changes letters rather than accents, tell me and I will check it
against the matcher first.

## 4. The pronunciation dictionaries are live

`elevenlabs/pronunciation/ro-voice.pls` (20 rules) and `hu-voice.pls` (36) are uploaded and attached.

| file | dictionary id | version id | attached to |
|---|---|---|---|
| ro | `AaMtnNwhZIwuKDy7zI1m` | `sllOUy0OaQibE5jPf78c` | `conversation_config.tts` |
| hu | `3uSfRsZV5XpeC3fdtKbV` | `jgpS5JvhL4HK73Dxvd4F` | `language_presets.hu.overrides.tts` |

The `en` preset keeps an empty locator list on purpose: it overrides no voice, so it speaks with the
Romanian voice and inherits the Romanian dictionary.

The drafts that existed before were keyed on evolvo's *stripped* spellings and would now fire on
almost nothing — the dictionaries had to be rebuilt after the names settled, not before. That
ordering is the whole reason this work ran in the sequence it did.

**Two things to know before you touch this config.**

**`language_presets` replaces, it does not merge.** Updating the agent with only the `hu` preset
silently deleted the `en` preset, and with it the English first message. I caught it by diffing the
response against the pre-update config and restored it in the next call — but nothing warned me, and
nothing would have warned you. Always send every preset you want to keep, and diff afterwards.

**Phonemes are reachable, contrary to what this document said earlier.** The public docs list
phoneme support for `eleven_flash_v2` and `eleven_v3` only, which would exclude
`eleven_v3_conversational`. But the agent carries a `conversation_config.tts.enable_phoneme_tags`
flag — *"phoneme tags, inline and from pronunciation dictionaries, are parsed into inline IPA"* —
currently `false`. Alias stays the default on merit: it works whatever that flag says, and a
respelling is a smaller judgement call than an IPA transcription nobody has heard yet. IPA is in the
file comments, so switching is mechanical if the listening test wants more precision.

**Editing a `.pls` needs a new upload and a new `version_id`** — a locator pins a version, so an
edited file changes nothing until the agent is re-pointed at it.

Two findings from building them, worth carrying into the listening test:

- **The Romanian voice was mispronouncing Romanian.** `Mures` is in 6 of the 8 addresses, so it was
  wrong on nearly every call. Now fixed upstream in n8n rather than by an alias.
- **`Optometrist` prefixes 9 of the 30 calendars** and Hungarian `s` = /ʃ/ makes it "Optometrisht"
  every time. Highest-value single entry in `hu-voice.pls`.
- Do **not** add `Ormenisan`, `Postei` or `Scolii` to the Hungarian file. The Hungarian voice reads
  those correctly *because* HU `s` = /ʃ/ is what the missing `ș` wanted. Only Romanian gets them wrong.

**Verified live, 2026-09-21 — 16 webhook calls, 25/25 executions successful, zero failures.**

**Not verified:** nothing in either `.pls` has been heard by a human. Every alias is a prediction
about how the engine reads a respelling. The two likeliest to be wrong are `Ifj` → `Ifiabb` in
Romanian (`Junior` is the other defensible reading — a judgement call about what a Romanian caller
expects) and the multi-word graphemes `Tg. Mureș` / `Gheorghe Doja`, which simply will not fire if
multi-word matching does not work. Both degrade to the un-aliased original rather than to something
wrong.

## 6. Two things about the API worth not rediscovering

**`calendarid` is not an id.** It is an ~800-character encrypted envelope regenerated on every call —
two responses 35 seconds apart returned the same 30 calendars with **0 of 30 matching `calendarid`
values**. Never persist one, never key anything on it, never store one on your side. There is no
stable key anywhere in the thirdpartyai API.

**`ai_public_names_hu/ro/en` exist on every calendar and are empty on all 30.** They are the
clinic-maintainable home for exactly this problem — per-language spoken names, owned by the clinic
rather than by a map in our workflow. Open question 11 with Imreh. If they ever get populated, the
`Display Names` map and half of both dictionaries become redundant.

## 7. The workflow export is trustworthy again

Earlier revisions of this document warned that `Optofarm-WIP.workflow.json` was stale and had to be
ignored. **That is no longer true** — it is refreshed, 126 nodes, and matches what is deployed.

It had been frozen at 115 nodes through four rounds of changes for a specific reason: the manual
tester's `get_auth.php` node carried the evolvo API key as a literal `Authorization: Bearer …`
header, so refreshing the export would have published a live credential to a public repository.

That is fixed at the source rather than by redacting on the way out. The node now authenticates the
same way the other eleven do, through the existing `Evolvo API Key` credential, so the key is gone
from the live workflow entirely — n8n's own `activeVersion` snapshot included — and exports are
clean by construction. It was the only hardcoded secret in 126 nodes.

**If you ever export the workflow yourself, dump only `name`, `nodes`, `connections`, `settings`.**
A raw `GET /workflows/<id>` also returns `staticData`, which holds a **live evolvo session token**;
`activeVersion`, a full mirror of `nodes` where a secret redacted from `nodes` alone survives; and
`shared`, which carries the owner's account details. I nearly published the key a second time this
way — the first clean-check passed on `nodes` and failed on the whole document.

### Still open, and it needs someone with clinic-side access

Moving the key into a credential did not revoke it. **It is still a live key and it is still in this
repository's git history**, so rotation with Imreh remains outstanding.

The same is true of the n8n webhook secret, with one extra wrinkle: it is readable in plaintext from
n8n's own execution data — every past call stores the `x-optofarm-secret` header — so **rotating it
alone does not close the hole.** The new value lands in the logs from its first call. That one needs
a different fix: shorter execution retention, or moving the check off a header n8n records.
